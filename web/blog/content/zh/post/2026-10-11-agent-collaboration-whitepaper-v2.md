## 0. 摘要

本规范解决一个具体问题：如何让 AI 执行代理能够独立完成代码推送、PR 创建、CI 跟踪与合并操作，同时保证它**永远无法直接修改主分支**，且所有凭证都**可控、可过期、可撤销**。

v2.0 在 v1.0 的基础上，把凭证模型从"推送凭证 / API 凭证"二分法细化为"每仓库凭证 / 共用推送凭证"的分工制：前者是每仓库一把、带完整操作权限的凭证，由代理平台加密保管；后者是多仓库共用、只有内容读写权限的凭证，只用于普通文件的 HTTPS 推送。两类凭证的权限边界、适用场景和禁止事项在本版中明确划分。

核心设计是三条：写哪个仓库就用哪个仓库的凭证（各管一摊，互不通用）；主分支由仓库级保护规则锁定，只能经 PR + CI 全绿进入；所有短期凭证有效期短、泄露时可一键作废。规范绑定的是角色（仓库所有者 / 执行代理 / 监控方），不绑定具体工具或代理产品——换代理不换规范。

**本文取代 v1.0，v1.0 保留作历史版本。** v1.0 原文见[《AI 代理协作开发规范白皮书 v1.0》](/post/2026-10-11-agent-collaboration-whitepaper/)。

## 1. 适用范围与角色

**适用仓库**：styrigx-space、styrigx-blog、styrigx-book。新增仓库必须先按第 6 节完成保护配置，才能纳入本规范。

**角色定义**：

| 角色 | 说明 |
|------|------|
| 仓库所有者（人） | 唯一有权签发、续期、撤销凭证的人；维护分支保护规则；对合并做最终确认。 |
| 执行代理 | 可替换的 AI 执行体（当前为 Muse）。按本规范操作仓库，不知道也不需要知道仓库之外的事。 |
| 监控方（只读） | 只读观察 CI 状态与部署结果，不执行任何写操作。 |

规范中的每一条都写明是约束谁的。所有者与代理的职责不对等：所有者负责"发钥匙和定门锁"，代理负责"按规矩进出"。

## 2. 设计原则

1. **最小权限**：共用推送凭证只有代码内容（Contents）的读写权限，没有管理仓库、改设置、删分支、改 workflow 的权力。理由：代理推送普通文件只需要推代码，给多了就是风险面。
2. **写哪个仓库用哪个仓库的凭证**：每仓库凭证只对自己的仓库生效，禁止跨仓库使用，也禁止用通用门户凭证代替。理由：一把钥匙只开一把锁，泄露时影响范围可控；跨仓库通用等于把所有仓库的命运绑在一起。
3. **主分支只能经 PR + CI 全绿进入**：任何人（含所有者）都不直接推主分支。理由：CI 是最后一道客观防线，绕过它等于放弃验证。
4. **凭证可过期、可撤销**：共用推送凭证有效期不超过 7 天，到期必须轮换；怀疑泄露时立即作废。理由：长期有效的凭证是定时炸弹，短有效期把损失窗口封死。
5. **保护规则对管理员同样生效**：分支保护规则的 bypass 列表必须为空。理由：规则若对所有者网开一面，代理迟早会"借用"这个口子——安全设计里不存在"可信的人可以例外"。
6. **换代理不换规范**：规范文本是交接的唯一依据，新代理上岗前必须通读并确认。理由：口头约定会随人员更替丢失，书面规范不会。

## 3. 凭证模型

| | 每仓库凭证 | 共用推送凭证 |
|---|---|---|
| **形态** | fine-grained 个人访问令牌 | fine-grained 个人访问令牌 |
| **可见性** | 由代理平台加密保管，代理看不到明文，只能通过平台网关调用 | 所有者直接交给代理（明文移交一次） |
| **权限** | Contents、Pull requests、Actions、Workflows 读写 | 仅 Contents 读写 |
| **生效范围** | 只对自己的仓库生效，一把只管一个仓库 | 多仓库共用（当前覆盖三个仓库） |
| **有效期** | 由平台管理，长期有效但可随时撤销重建 | 不超过 7 天，到期轮换 |
| **用途** | 开 PR、查 CI 状态、更新分支、合并 PR、重跑 Actions、修改 `.github/workflows/` | 只用于普通文件的 HTTPS `git push` |
| **存储** | 平台加密存储 | 代理存入 git credential helper |

**必须**：写哪个仓库，就必须用那个仓库的凭证。禁止用其他仓库的凭证，也禁止用通用门户凭证代替。理由：凭证与仓库一对一绑定，审计时能精确追溯"谁动了哪个仓库"；混用会让一次泄露同时击穿多个仓库。

**必须**：两类凭证不混用。共用推送凭证禁止拿来调 API、改 workflow、重跑 Actions、改 ruleset；每仓库凭证禁止出现在 git 传输层（不嵌入 remote URL）。理由：混用会让一次泄露同时击穿两个平面；workflow 文件控制 CI 跑什么，改它的权限必须与合并 PR 的权限在同一把钥匙上。

**为什么不用 SSH deploy key**：代理的运行环境可能封锁 SSH 协议（出站代理只放行 HTTPS），此时 deploy key 完全不可用。deploy key 列为未来可选项——当且仅当网络放行 SSH 时才考虑，且仍需每仓库独立一把。理由：选型必须基于"在当前网络下真实可用"，而不是"理论上更优雅"。

**修改 `.github/workflows/` 的规范**：

1. **应当**在本地改好并测试通过，再提交。理由：workflow 改错会导致整个 CI 瘫痪，本地验证是最后一道防线。
2. 提交时**必须**用对应仓库的每仓库凭证（`git push` 或 Contents API 都可以）。理由：改 workflow 的权限与合并 PR 的权限应当在同一把钥匙上，共用推送凭证没有这个权限。
3. **Contents API 与 Git Data API 的区别**：
   - Contents API 是单文件提交接口：一次只改一个文件，生成一个普通 commit，走正常的 git 历史。**允许**用于提交 `.github/workflows/` 这类单文件修改（当 git push 因权限不足被拒时）。
   - Git Data API 允许不经本地 git 历史直接在远端造提交（建 blob / tree / commit、改 ref），绕过了本地测试与提交审查，生成的提交无法在本地复现和验证。**禁止**在任何分支使用 Git Data API 做任何写操作。
   - 理由：Contents API 的结果与本地 `git commit + push` 等价，可审计、可复现；Git Data API 绕过了本地历史，不可审计。允许前者是为了解决权限问题，不是为绕过流程。

**为什么禁止 Git Data API**：Git Data API 允许不经本地 git 历史直接在远端造提交（建 blob / tree / commit、改 ref），绕过了本地测试与提交审查，生成的提交无法在本地复现和验证。**禁止**在任何分支使用 Git Data API 做任何写操作。理由：可复现性是工程协作的底线，绕过本地历史的提交不可审计、不可回滚验证。

## 4. 分支保护

每个仓库必须配置一个保护主分支的 ruleset：

| 配置项 | 取值 | 理由 |
|---|---|---|
| 状态 | Active | 规则必须处于启用状态，草稿规则等于没有。 |
| Bypass 列表 | 为空 | 对管理员同样生效，见第 2 节原则 5。 |
| 目标 | 默认分支（main） | 只保护主分支，功能分支不受限，保持开发灵活。 |
| 删除保护 | 禁止删除分支 | 防止误删主分支。 |
| Force push | 禁止 | 历史必须只能追加，不能改写；改写历史会让已合并的审计链断裂。 |
| 必须 PR | 是 | 任何进入主分支的变更都必须经过 PR。 |
| PR 审批数 | 0（不开"最后推送者须他人批准"） | 单人仓库开此项会导致自己永远合并不了——自锁。审批由 CI 与所有者的线下确认代替。 |
| 必过检查 | 见下表 | CI 全绿是合并的硬门槛。 |
| 分支必须最新 | 是 | 合并前必须 rebase 到最新主分支，防止合并过期代码。 |

**必过检查对照表**：

| 仓库 | 必过检查 |
|------|----------|
| styrigx-space | quality、passkey-e2e |
| styrigx-blog | build-and-deploy |
| styrigx-book | build-and-deploy |

**必须**：必过检查填的必须是仓库 CI 里**真实存在**的检查名。理由：填一个不存在的名字，合并会被永久卡住——GitHub 会一直等一个永远不会来的检查。这是真实踩过的坑。

## 5. 标准开发流程

1. **开功能分支**：从最新主分支开出，分支名体现用途。禁止直接在主分支上写代码。
2. **本地测试**：构建、单元测试、相关 e2e 必须在本地跑通再推。理由：把 CI 当本地测试的替代品是浪费所有人的时间。
3. **`git push` 功能分支**：只用共用推送凭证经 HTTPS 推送普通文件；改 `.github/workflows/` 时必须用对应仓库的每仓库凭证。禁止推送主分支。
4. **开 PR**：标题带版本/类型前缀；描述如实记录开发中的异常（如 CI 曾失败、修过什么），不隐瞒。理由：PR 描述是审计记录，隐瞒异常等于伪造审计。
5. **按文件添加，禁止批量添加**：**禁止** `git add -A` / `git add .`，必须按文件名逐个 `git add`；提交前必须看 `git status` 确认。理由：批量添加会把占位文件、本地构建产物或误改的文件夹带进提交，曾真实发生过把未完成的占位文件推进主分支的事故。
6. **等 CI**：CI 没出结果前不做合并操作；失败了先在本地定位、做真正修复再推。**禁止**重跑别人的失败任务来"刷绿"、**禁止**删测试或降阈值来过 CI、**禁止**改测试去迎合实现（测试不通过应当修实现，不是放松断言）。
7. **新增测试必须接入 CI**：只在本地跑过的不算数。理由：本地跑过只能证明"这次行"，接入 CI 才能保证"每次都行"；没有进 CI 的测试等于没有测试。
8. **分支落后主分支时**：
   - 无冲突：调 update-branch 接口同步。
   - 有冲突：本地 `git merge main` 解决冲突，跑完全部测试，普通 `git push`（禁止 force push）。
   - 解决不了：停下，把冲突详情报告给所有者，不绕路。
9. **CI 全绿后合并**：用合并接口（merge commit 方式）合并 PR。
10. **线上验证**：合并后确认生产部署成功，做冒烟验证（首页状态、关键接口），有问题立即报告。
11. **每次交付必须报告**：仓库名、PR 号、CI run 号、结果（成功/失败）、HEAD commit。理由：所有者需要凭这四个要素追溯任何一次变更，缺一个就断链。

## 6. 所有者职责清单

- [ ] **签发 / 续期 / 撤销共用推送凭证**：到期前签发新的；怀疑泄露时立即撤销。撤销后通知代理旧凭证作废。
- [ ] **维护各仓库的每仓库凭证**：凭证过期或平台变更时及时重建，保证代理的 PR / 合并 / workflow 修改操作不断链。
- [ ] **维护分支保护规则**：CI 流水线改名或增删检查时，同步更新"必过检查"（否则合并永久卡住，见第 4 节）。
- [ ] **新仓库准入**：新仓库必须先建好保护规则、配好专属的每仓库凭证，再加入共用推送凭证。**禁止**把未受保护的仓库加入共用凭证——一把钥匙开多把锁，每把锁都必须是好锁。
- [ ] **合并确认**：对高风险 PR（如改鉴权、改部署配置）做合并前的人工确认。
- [ ] **实机验收**：需要真机或生产环境验证的改动（如移动端交互、锁屏流程），由所有者在生产环境实机验收后再确认合并。

## 7. 代理职责与禁止清单

**应当做的**：

- 只推送功能分支；PR 描述如实记录异常；CI 失败时先本地定位再修；token 失效时只向所有者申请新的；每次交付报告仓库、PR、run 号、结果。

**权限错误的自助处理**：

遇到 403 或「without workflow scope」类报错时，代理**必须**按以下顺序自助处理，**禁止**直接打断所有者：

1. 先确认自己用的是哪个仓库的凭证，是否拿错了仓库的凭证或误用了共用推送凭证。
2. 换成对应仓库的每仓库凭证，重试一次。
3. 按以上规则试过两次仍失败，再向所有者报告：完整报错原文、用的是哪把凭证（按"某仓库的每仓库凭证 / 共用推送凭证"描述，不写真实名称）、在哪一步失败。

理由：权限问题多半是拿错钥匙，代理自己换一把再试就能解决；动不动就打断所有者，会把所有者的注意力耗尽在本来可以自助解决的问题上。

**需要实机验收的改动**：

1. 先开 draft PR，CI 全绿后通知所有者。
2. 所有者在生产环境实机验收（如三星浏览器上的交互流畅度、锁屏流程）。
3. 验收通过后再转正式 PR 并合并；不通过就开 revert PR 回滚，几分钟内可退回。

理由：子站会话凭证只在正式域名下生效，预览域名（如 pages.dev）拿不到主站的解锁凭证，被保护页面会直接跳锁屏，等于无法验收；且本次这类改动出问题会自动退回整页跳转，风险可控，回滚成本低。

**禁止做的**：

| 禁止项 | 理由 |
|--------|------|
| 推送主分支 | 主分支只能经 PR 进入，见第 2 节原则 3。 |
| force push | 会改写已推送历史，破坏审计链；且保护规则本身就禁了。 |
| 使用 Git Data API 做写操作 | 绕过本地历史与测试，不可复现，见第 3 节。 |
| 两类凭证混用 | 扩大单次泄露的影响面，见第 3 节。 |
| 用共用推送凭证改 workflow / 重跑 Actions / 改 ruleset | 共用凭证没有这些权限，见第 3 节。 |
| 打印 token、把 token 写进 remote URL / 仓库文件 / 日志 / PR 描述 | 任何持久化或传播 token 的行为都是泄露。 |
| token 失效后自行换通道（如改 SSH、换 API） | 凭证通道由所有者决定，代理无权自选；应当停下并申请新 token。 |
| 确认后向 PR 追加提交 | 合并的代码必须与确认时看到的一致；要改就开新 PR 或重新确认。 |
| 隐瞒 CI 失败或测试缺口 | 审计记录必须真实，见第 5 节第 4 步。 |
| `git add -A` / `git add .` | 会把占位文件和本地产物夹带进提交，见第 5 节第 5 步。 |
| 更新已有的视觉基线 | 基线是"长什么样算对"的标准答案，更新它等于改答案；只能为新页面新增基线。视觉失败时先查共同原因（如字体环境、数据源变化），而不是先怀疑基线。 |
| 改测试去迎合实现 | 测试是需求的 executable 形式；测试不通过说明实现错了，应当修实现。 |
| 新增测试不接入 CI | 没进 CI 的测试等于没有测试，见第 5 节第 7 步。 |

## 8. 轮换与事故响应

**到期轮换流程**（所有者签发新 token 后，代理执行）：

1. `git credential reject` 清掉旧凭证（按存储时的 protocol/host/username 定位）。
2. `git credential approve` 存入新凭证。
3. 用一次无害的 push（如 `--dry-run`）验证新凭证有效。

**疑似泄露响应**（所有者执行，代理配合）：

1. 立即在平台侧撤销该 token（revoke），不要等确认——**应当**先断后查。
2. 重新签发新 token，按轮换流程交给代理。
3. 检查泄露窗口期内的分支推送记录和 PR，确认没有异常提交。

**必须**：轮换期间旧 token 撤销与新 token 生效之间，代理**禁止**用任何其他方式推送来"赶工"。理由：空窗期的"变通"正是事故的温床。

## 9. 更换代理交接清单

更换执行代理（或代理平台）时，按序执行：

- [ ] 撤销旧的共用推送 token（所有者）。
- [ ] 在新代理平台重新登记各仓库的每仓库凭证（所有者）。
- [ ] 签发新的共用推送 token 交给新代理（所有者）。
- [ ] 新代理通读本白皮书全文，并向所有者确认已理解（书面确认）。
- [ ] 新代理用一个空功能分支（只改一行注释）跑通"推送 → 开 PR → CI → 关闭 PR"全流程，验证两类凭证都工作。
- [ ] 确认新流程跑通后，在旧代理平台删除其保管的每仓库凭证。

**禁止**跳过第 5 步直接让新代理接手生产 PR。理由：交接验证必须用无害操作完成，不能拿真实发布练手。

## 10. 附录

### A. ruleset 配置逐项表

见第 4 节"分支保护"表格。补充说明：ruleset 的 enforcement 设为 Active；bypass  actors 为空数组；`required_status_checks` 填第 4 节对照表的检查名；`required_pull_request_reviews` 中 `required_approving_review_count` 为 0 且不开" dismissed stale reviews"之外的额外限制（单人仓库）。

### B. git credential 配置示例

共用推送凭证只存一条，不按仓库区分（多仓库共用同一把 token）：

```
protocol=https
host=github.com
username=x-access-token
password=<TOKEN>
```

存入：`git credential approve`（从标准输入读入以上四行加空行）；清除：`git credential reject`（读入前三行加空行）。`<TOKEN>` 为占位符，真实 token 只在所有者与代理的直接移交中出现一次，不写入任何文件。

各仓库的 remote 统一用不带凭证的 HTTPS 地址，形如 `https://github.com/<owner>/<repo>.git`。**禁止**把 token 嵌入 remote URL（`https://<token>@github.com/...` 形式）——URL 会出现在日志、报错和进程列表里。
