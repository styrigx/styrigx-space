This round rebuilt the site's colour system. In one sentence: **light/dark modes and custom accent colours are gone, and each palette now has exactly one look.** Of the 22 palettes, 8 are light and 14 are dark; the default is Terra, a dark one. The "Light / Dark / System" segmented control in the quick panel is gone, leaving only the palette grid and "reset".

![The homepage under all 22 palettes (desktop 1440×900), each card labelled with its id and light/dark](/blog/img/2026-11-12/palettes-home.webp)

## Why drop light/dark modes

In the old system a palette was a "seed": the same set of colours had to produce both a light and a dark version, and users could also swap the primary colour with a picker. Flexible on paper, but with three real problems.

**Combinatorial explosion.** 22 palettes × 2 modes is 44 colour schemes, and arbitrary custom accents make the space infinite. The contrast audit could only cover presets; a bad custom colour could only be patched at runtime: the engine recomputed the roles in the browser, cached them in localStorage and read the cache on the next visit. That path had its own scripts, its own cache and its own invalidation rules, wired separately into all four sites.

**Half of the schemes were by-products.** Dusty Blue, Champagne and Cream were designed for light backgrounds. Flip them to dark and you get a near-black with a hint of hue, indistinguishable from the other dark palettes. The reverse is also true: the light versions of Lake, Indigo and Berry were just "white with a tint". Of the 44, the ones with real character were essentially each palette's "native" side.

**First paint had to guess.** Following the system meant first paint had to read `prefers-color-scheme`, then the manual choice in the cookie, then the palette, and combine all three to know what to draw. The sub-sites (the blog, Curio, Daymark) had to inherit the same logic from the main site's cookie. Get the order wrong anywhere and the page flashes the other mode first.

So the trade-off this time: **a palette is one designed look.** If you want dark, pick one of the dark palettes; if you want light, pick a light one. The choice becomes "pick a colour scheme you like", not "pick a scheme × pick a mode × maybe pick a colour".

## Splitting light and dark: OKLCH lightness 0.6

Whether a palette is light or dark is not hand-labelled. The background decides:

```js
// palette-scheme.js
export function paletteMode(bg) {
  const L = hexToOklch(bg).l;
  return L >= 0.6 ? 'light' : 'dark';
}
```

OKLCH rather than HSL lightness, because OKLCH lightness is calibrated to human perception: in HSL a yellow and a blue at the same L = 50% look very bright and very dark respectively; in OKLCH two colours with the same L look about equally bright. The 0.6 threshold sits in a wide gap between the two groups: all 8 light backgrounds are around L ≈ 0.955 and all 14 dark ones around L ≈ 0.19–0.20, so no palette sits on the line.

The split:

| Mode | Count | Palettes |
|---|---|---|
| Light | 8 | Dusty Blue, Glacier, Sage, Coral, Mustard, Champagne, Dusty Rose, Cream |
| Dark | 14 | Lake, Indigo, Teal, Violet, Forest, Matcha, Cherry, Tangerine, Terra, Amber, Rose, Berry, Orchid, Graphite |

The dark side is larger on purpose: the site is terminal-styled, and a dark background suits it.

## Seven colours

Each palette exposes only seven colours, each with a fixed job:

| Role | Used for |
|---|---|
| Background | Page background and the background ladder; no text cards directly on it |
| Surface | Cards, panels, the top bar, terminal windows and other neutral surfaces |
| Text | Body text |
| Primary | Main interaction: primary buttons, links, focus rings, selected states |
| Secondary | Secondary actions, category icons |
| Tertiary | Badges and local accents on special cards |
| Accent | Tags, charts and other low-frequency decoration |

The other few dozen tokens (the seven background steps `--sgx-bg-1..7`, the `-on` / `-tint` / `-ink` steps of each foreground colour, borders, dividers) are all derived from these seven by one set of formulas. No palette is hand-tuned: a unit test asserts there are no per-palette overrides in the spec. The upside is that changing a formula changes all 22 palettes; the downside is that the formula has to hold for every one of them, so the audit runs on every palette (see below).

**Terra is pinned.** Terra is the default, the first thing a new visitor sees, so its background, surface and text skip the formulas and are pinned: background `#161412`, surface `#1d1b19`, text `#ece6dc`. A warm near-black and an off-white with an OKLCH chroma of only about 0.005: almost neutral, but a little warmer than pure grey. The other 13 dark backgrounds carry a clear hue (C 0.03–0.065); only Graphite stays a cool grey (C about 0.011).

## Fixed semantic colours

Success, error, warning and info used to be mixed from the palette: in a palette whose primary leaned green, "success" leaned with it. In practice that meant that in some palettes "success" and the primary were nearly the same colour, and you couldn't tell a button from a success message.

They are now fixed, with only a light and a dark set:

| Set | Success | Error | Warning | Info |
|---|---|---|---|---|
| Light | `#097334` | `#be2423` | `#864e00` | `#1666aa` |
| Dark | `#39e175` | `#ff6f69` | `#ffa521` | `#5aa5ff` |

The dark set is the more saturated option. Across every text surface of all 14 dark palettes the minimum contrast is 4.80:1, and on the surface colour it is generally above 5.8:1. The audit only checks the semantic colours and never changes them: if a future palette makes them fail, the build fails, instead of the colours being quietly adjusted.

One known compromise: Graphite's primary is blue, and so is info. Rather than give Graphite its own info colour, the two are told apart by the i icon and the wording on the message. Colour should never be the only channel for information anyway.

## A fixed code theme

Blog code blocks used to follow the palette too: keyword, string and comment colours were mixed from the foreground colours. Same problem as the semantic colours: in some palettes strings and keywords clashed, and readability varied with the palette.

Syntax highlighting is now a fixed theme with just a light and a dark variant, outside the palette. Whatever palette you pick, the same code looks the same, which is how most editors work: the UI theme and the syntax theme are separate things. Audit thresholds: tokens ≥ 4.5:1 on the code background, plain code ≥ 7:1, line numbers ≥ 3:1.

## Auditing contrast

The target is WCAG 2.x level AA:

- body text against its background ≥ 4.5:1;
- controls (button edges, focus rings, switches) ≥ 3:1;
- "night cards", deliberately high-contrast cards, ≥ 7:1.

The audit lives in the generator. When `gen-palettes.mjs` generates each palette's tokens it runs `audit()`, and any failing check exits non-zero; CI runs the generators with `--check`, so generated files that drift from the source also fail.

Text is the most fragile. The same body colour sits on the background, the surface and various card surfaces, and has to reach 4.5:1 against **every** text surface. That is what `fitInks` in the engine does: starting from the palette's text colour, it moves step by step along OKLCH lightness, darker for light palettes and lighter for dark ones, until every surface passes, keeping hue and chroma as they are. Body text on the surface colour now measures 16.8–17.1:1 across the light palettes and 13.3–13.8:1 across the dark ones.

The other easily missed case is text on buttons. The primary itself may be a mid-tone (Dusty Blue's primary is the mustard `#d4a72c`), where white text fails and dark text may not be enough either. The engine computes an `-on` colour per foreground colour: it picks whichever of a dark ink and white reaches 4.5:1 against it, tries a deeper ink or pure white if neither does, and as a last resort nudges the fill itself away from the text colour. Text uses `-ink`, fills use the base colour, and text on a fill uses `-on`. Keeping the three apart means a whole button never again gets darkened to olive brown just so white text reads on it.

## First paint and old cookies

All four sites share one first-paint reader, `ui-cookie-read.js`. It runs synchronously in `<head>`, and its job is now short:

1. read the palette id from the `sgx-ui` cookie (Terra if there is none);
2. set `data-palette` on `<html>` and add or remove the `dark` class according to that palette's mode;
3. set `color-scheme` and `<meta name="theme-color">` so scrollbars, form controls and the phone status bar follow.

It **no longer reads** `prefers-color-scheme`, so there is no "system is dark but the palette is light" case to reconcile. When the system switches between light and dark, the page stays as it is. That is intended.

On compatibility, the `sgx-ui` cookie stays at structure version v2: new code no longer writes the `mode` and `accent` fields, and the reader simply ignores them. Old cookies still yield their palette; only the old dark mode and custom accent no longer apply. Someone who had chosen "Dusty Blue + dark" now sees the light Dusty Blue. First paint also clears the old `sgx-theme-mode`, `sgx-accent` and the runtime role cache, so stale data doesn't linger in localStorage.

The terminal command changed with it: `theme` now takes a palette id directly, `theme lake` switches to Lake, and completion lists all 22.

## What was deleted

This change removes more code than it adds. Five files went entirely:

- `lib/theme.js`: light/dark modes and following the system;
- `lib/accent.js` and `lib/accent-roles.js`: the runtime engine and role cache for custom accents;
- a `shell-accent.js` each in Curio and Daymark: the glue that brought custom accents to the sub-sites;
- the blog's `entries/inherit.ts`: how the blog inherited the main site's mode and custom accent.

Also gone: the MODE section of the quick panel, its i18n strings, the mode and accent entries in cloud sync, and a batch of CSS that only existed for them.

## Tests

Several layers guard the change:

- **Unit tests**: the engine's audit rules, a per-palette check of all 22, the quick panel swatches, the terminal `theme` command and the cloud sync entries;
- **A contract fixture**: 36 cases in `ui-cookie-contract.json` covering new cookies, old cookies (with mode / accent) and malformed ones; the readers on the main site and all three sub-sites must give the same answer;
- **End-to-end tests**: no mode section in the quick panel, switching between light and dark palettes changes the whole page, sub-sites match the main site, and the system's light/dark setting doesn't affect the page;
- **Visual regression**: one light and one dark palette (Dusty Blue and Terra) as screenshot baselines. Since the colours changed across the board, the baselines need to be re-shot once.

## Wrapping up

At heart this change is a subtraction: a system that could combine into endless looks becomes 22 designed and audited ones. It is less flexible, but every palette is now fixed: fixed colours, fixed contrast, fixed first paint. For a personal site, that's what I'd rather have.
