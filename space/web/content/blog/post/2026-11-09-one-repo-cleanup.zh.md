上一篇写的是看得见的改版。这一篇写看不见的那一半：仓库、部署和数据。这部分没有截图，但它决定了以后改东西要花多少力气。

## 以前：一个站一个仓库

最早每个站点一个仓库、一个子域名：主站、`blog.styrigx.com`、`book.styrigx.com`，后来又多了一个承载奇趣和日刻的图志仓库。每个站有自己的 Pages 项目，各自同步一份共享外壳（顶栏、面板、调色板那一套）。

问题很快就出来了：

- 外壳副本经常不同步，改一个按钮要发四个 PR；
- 锁屏要跨子域共享会话，cookie、公钥分发、跨站回跳，出错面很大；
- 四次构建、四套 CI、四份依赖升级。

## 现在：一个仓库、一个域名、一个 Hugo 站

10 月下旬到 11 月 8 日，分几步做完了合并：

1. 子站代码全部搬进主站仓库，旧仓库归档；
2. 子站换到同一个域名下按路径分：`/blog/`、`/curio/`、`/daymark/`，旧子域名下线；
3. 最后一步把四个站合成**一个 Hugo 站**，一份配置，一次构建，一个 Pages 项目发布。

共享外壳不再复制：子站直接用主站的模板和脚本，只有少量派生文件由脚本生成，CI 检查它们和源头一致。

代价也写清楚：任何一个站构建失败，四个站一起发不出去；子站的中文地址要在 front matter 里写死，写错直接构建失败。我能接受，宁可失败得早、失败得响。

## L 系列：进站后端换名、搬库

进站 V3 的设计定下来之后（见另一篇），后端也要跟着理顺。我把它拆成五个 PR，按顺序上：

- **L0**：日刻数据里有个标记值叫 `admin`，表示的其实是「经账号授权写入」，先改成 `grant`，把 `admin` 这个词让出来（进站侧的身份在代码里要用它）；
- **L1**：进站界面改版——`sudo styrigx`、盾牌下拉、环境提示符；
- **L2**：进站后端改名为 space-core，和奇趣、日刻的 `<站>-core` 命名对齐；分享短链原本是单独的 Worker，并进 core；
- **L2b**：数据搬到新的 core 数据库和 KV；服务监测拿到自己的数据库；
- **L3**：删掉只为切换存在的一次性搬迁代码，并给自动回滚加了下限，不会退回到切库之前的版本。

监测为什么单独拆出来？两天前我刚把网关、短链、监测三个库合成一个，这次又分开了。想清楚的规则是：**跟站点进站有关的进 core；功能上独立于站点的（账号、AI、监测、代理规则）各自独立。** 合库的时候只想着「少一个资源」，没想清楚边界。

现在一共 7 个 Worker：站点核心、账号、AI、监测、奇趣、日刻、代理规则。只有站点核心挂在整站路由上，其余要么只管自己的接口路径，要么没有公开路由，只能经服务绑定调用。

切换有代价：换签名钥匙和密码的盐时，所有设备回了一次锁屏，旧的临时钥匙作废。这是设计时就接受的一次性成本。

## 大扫除

L 系列上线核对之后，开始删东西。规则只有一条：**先在 main 的代码和配置里确认没人读，再删。**

平台上：

- Cloudflare：两个旧 Worker、旧数据库、旧 KV、一个旧部署 token、一批已经没人读的旧密钥，以及账号库里 8 张早就空了的遗留表；
- GitHub：两个旧部署环境，二十多条已经合并或关闭的分支，一批过期的 Actions 缓存和构建产物。

仓库里：

- 删了没有任何引用的一次性脚本、旧测试夹具、没进构建的 JS 和模板片段。删之前分支和 main 各构建一次，逐文件比较产物，确认只差构建时间戳，页面零变化。

## 文档重写成一本规范书

以前 `docs/` 里堆着任务书、设计稿、历史方案，新旧混在一起，读的人（包括 AI 代理）分不清哪份是现行的。这次整个重排：

- 按用途分目录：架构、规范、安全、设计、运维、贡献，外加决策记录（ADR）；
- 每份文档开头有编号、版本、日期、状态；规范性用语按 RFC 2119 解释；
- **代码优先**：文档描述的是 main 上代码的现状，冲突时以代码为准，并且在同一个 PR 或紧随其后的 PR 里改文档；
- **过时即改**：过时的文档直接改写或删除，不留「历史」副本；来龙去脉写进 ADR，或者留在 git 历史里；
- 只写资源和密钥的名字，不写任何值和内部 id。

整理的时候顺手对了一遍文档和代码，找出十来处不一致，全部按代码改正。四份 ADR 记下了这段时间最大的四个决定：一个仓库一个站、锁屏方案的演进、账号与进站 V3、AI 模型选择。

最后重写了根目录的 README（中英两份），重拍了 16 张截图（首页、锁屏、AI、博客，手机和 DeX，中英各一套）。

## 一点感想

这几天的大部分平台操作和代码是 AI 代理按我批准的范围做的：搬库、改名、删资源、开 PR、盯 CI。我负责定设计、建密钥、点头合并。能这么放手，靠的是前面那套规矩——只走 PR、不直推 main、CI 全绿才合、密钥的值永远只经我手，以及删东西之前先证明它没人用。
