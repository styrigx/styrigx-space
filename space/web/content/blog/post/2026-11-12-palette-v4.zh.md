这一轮把站点的配色系统重做了一遍。改动用一句话说：**删掉深浅模式和自定义主题色，每套调色板只有一个样子。** 22 套里 8 套是浅的，14 套是深的，默认是深色的陶土。快捷面板里原来那排「浅 / 深 / 跟随系统」的分段按钮没了，只剩调色板网格和「恢复默认」。

![22 套调色板下的首页（桌面 1440×900），每张卡标注 id 和深浅](/blog/img/2026-11-12/palettes-home.webp)

## 为什么删深浅模式

旧系统里，一套调色板是一个「种子」：同一组颜色既要生成浅色版，也要生成深色版，用户还可以用拾色器换掉主色。看起来很灵活，实际有三个问题。

**组合爆炸。** 22 套 × 2 种模式就是 44 种配色，再加上任意自定义色，状态空间是无限的。对比度审计只能覆盖预设，自定义色出了问题只能在运行时兜底：引擎在浏览器里重新算一遍角色色、缓存到 localStorage，第二次打开再读缓存。这条链路有自己的脚本、自己的缓存、自己的失效规则，四个站各接一遍。

**一半的配色是「顺带生成」的。** 雾霾蓝、香槟金、奶油白这类颜色，本来就是为浅底设计的；把它们翻成深色，得到的是一块带点色相的近黑底，和别的深色套看不出区别。反过来，湖蓝、靛蓝、莓果的浅色版也只是「白底加一点色」。44 种里真正有辨识度的，大约就是每套「本来的那一面」。

**首帧要猜。** 跟随系统意味着首帧要读 `prefers-color-scheme`，再读 cookie 里的手动选择，再读调色板，三者合起来才知道画什么颜色。子站（博客、奇趣、日刻）还要从主站的 cookie 继承同一套判断。任何一环顺序不对，就会先闪一下另一种模式。

所以这次的取舍是：**一套调色板 = 一个设计好的样子。** 想要深色就选深色的那几套，想要浅色就选浅色的那几套。选择变成了「挑一个喜欢的配色」，而不是「挑配色 × 挑模式 × 可能再挑一个颜色」。

## 深浅怎么分：OKLCH 亮度 0.6

每套调色板是浅还是深，不手动标，由底色决定：

```js
// palette-scheme.js
export function paletteMode(bg) {
  const L = hexToOklch(bg).l;
  return L >= 0.6 ? 'light' : 'dark';
}
```

用 OKLCH 而不是 HSL 的 L，是因为 OKLCH 的亮度是按人眼感知校准的：HSL 里同样 L = 50% 的黄色和蓝色，看起来一个很亮一个很暗；OKLCH 里 L 相同的两种颜色，看起来就差不多亮。阈值 0.6 落在两组之间很宽的空档里——现在 8 套浅色的底都在 L ≈ 0.955，14 套深色的底都在 L ≈ 0.19–0.20，不存在「卡在线上」的套。

分出来是这样：

| 模式 | 数量 | 调色板 |
|---|---|---|
| 浅 | 8 | 雾霾蓝、冰川蓝、鼠尾草绿、珊瑚、芥末黄、香槟金、干枯玫瑰、奶油白 |
| 深 | 14 | 湖蓝、靛蓝、青碧、紫、山绿、抹茶、樱桃、橘子、陶土、琥珀、蔷薇、莓果、兰紫、石墨 |

深色的套多，是有意的：这个站本来就是终端风格，深底更像它自己。

## 七个颜色

每套调色板对外只有七个颜色，各有固定的职责：

| 角色 | 用途 |
|---|---|
| 底 | 页面底色和背景阶梯，不直接放文字卡片 |
| 面 | 卡片、面板、顶栏、终端窗口等中性表面 |
| 字 | 正文 |
| 主 | 主交互：主按钮、链接、焦点环、选中态 |
| 辅 | 次要操作、分类图标 |
| 第三 | 徽标、特殊卡片的局部撞色 |
| 点缀 | 标签、图表这类低频装饰 |

其余几十个 token——背景七档 `--sgx-bg-1..7`、每个前景色的 `-on` / `-tint` / `-ink` 三档、边框、分隔线——都由这七个颜色按同一套公式算出来。没有任何一套是「手调」的：单测会断言规格里没有逐套覆盖的值。好处是改公式就能改全部 22 套，坏处是公式必须对每一套都成立，所以审计要跑在每一套上（见下文）。

**默认陶土钉值。** 陶土是默认调色板，第一次来的人看到的就是它，所以它的底、面、字三个颜色不走公式，直接钉死：底 `#161412`、面 `#1d1b19`、字 `#ece6dc`。这是一组暖调的近黑和米白，色度（OKLCH C）只有 0.005 左右，几乎是中性的，但比纯灰多一点温度。其余 13 套深色的底都带明显色相（C 0.03–0.065），只有石墨保留冷灰（C 约 0.011）。

## 语义色写死

成功、错误、警告、信息四个颜色，旧系统里是从调色板混出来的：主色偏绿的套，「成功」就跟着偏一点。这带来一个很实际的问题——在某些套里，「成功」和主色几乎是一个颜色，用户分不清这是一个按钮还是一条成功提示。

这次改成写死，只按深浅分两档：

| 档 | 成功 | 错误 | 警告 | 信息 |
|---|---|---|---|---|
| 浅 | `#097334` | `#be2423` | `#864e00` | `#1666aa` |
| 深 | `#39e175` | `#ff6f69` | `#ffa521` | `#5aa5ff` |

深色档选的是饱和度更高的一组，在 14 套深色的所有正文表面上，最低对比度是 4.80:1；在「面」上普遍在 5.8:1 以上。审计对语义色只校验、不改值：如果哪天新加的一套让语义色不达标，构建会直接失败，而不是悄悄把颜色调掉。

有一个已知的折中：石墨的主色是蓝，信息色也是蓝。这里没有为它单独换颜色，而是依靠提示条上的 i 图标和文字来区分——颜色从来不该是唯一的信息通道。

## 代码高亮固定主题

博客代码块原来也跟着调色板走：记号、字符串、注释的颜色从前景色混出来。问题和语义色一样，在某些套里字符串和关键字撞色，可读性随调色板波动。

现在代码高亮是一份固定的主题，只分浅、深两档，不计入调色板。不管选哪套，同一段代码看起来都一样，这也是大多数编辑器的做法：界面主题和语法主题是两回事。审计标准：记号对代码底 ≥ 4.5:1，正文 ≥ 7:1，行号 ≥ 3:1。

## 对比度怎么审

目标是 WCAG 2.x 的 AA 级：

- 正文文字对背景 ≥ 4.5:1；
- 控件（按钮边界、焦点环、开关）≥ 3:1；
- 「夜间卡」这类刻意做成高对比的卡片 ≥ 7:1。

具体做法是把审计写进生成脚本。`gen-palettes.mjs` 生成每一套的 token 时会跑一遍 `audit()`，任意一条不达标就退出非零；CI 对生成物跑 `--check`，生成物和源码不一致也会失败。

最容易出问题的是「字」。同一个正文颜色要放在底、面、各种卡片表面上，必须对**每一个**正文表面都 ≥ 4.5:1。引擎里的 `fitInks` 做的就是这件事：从调色板的字色出发，沿 OKLCH 亮度方向一点点压深（浅套）或提亮（深套），直到对所有表面都达标，色相和色度尽量不动。现在 22 套的正文对「面」的对比度是：浅套 16.8–17.1:1，深套 13.3–13.8:1。

另一个容易忽略的是按钮上的字。主色本身可能是中间调——比如雾霾蓝的主色是芥末黄 `#d4a72c`——白字压不住，黑字又未必够。引擎对每个前景色单独算 `-on`：在深墨和白之间挑一个对它 ≥ 4.5:1 的；两个都不够时，再把填充色往反方向推一点。文字用 `-ink`、填充用本色、文字放在填充上用 `-on`，三者分开，就不会再出现为了白字可读、把整块按钮压成橄榄棕的情况。

## 首帧和旧 cookie

四个站共用一个首帧读端 `ui-cookie-read.js`。它在 `<head>` 里同步执行，做的事情现在很简单：

1. 读 `sgx-ui` cookie 里的调色板 id（没有就用陶土）；
2. 在 `<html>` 上写 `data-palette`，按这套的模式加或去掉 `dark` 类；
3. 写 `color-scheme` 和 `<meta name="theme-color">`，让滚动条、表单控件和手机状态栏跟着变。

它**不再读** `prefers-color-scheme`，也就不存在「系统是深色、调色板是浅色」需要调和的情况。系统切换深浅时页面不动，这是预期行为。

兼容方面，`sgx-ui` cookie 的结构版本仍是 v2，没有升级：新代码不再写 `mode`、`accent` 字段，读端遇到旧字段直接忽略。所以老用户的 cookie 照样能读出调色板，只是原来的「深色模式」和自定义主题色不再生效——一个选了「雾霾蓝 + 深色」的人，现在看到的是浅色的雾霾蓝。首帧同时会清掉旧的 `sgx-theme-mode`、`sgx-accent` 和运行时角色缓存，避免旧数据留在 localStorage 里。

终端命令也跟着变：`theme` 现在直接接调色板 id，`theme lake` 切到湖蓝，补全列出全部 22 套。

## 删了什么

这次净删除的代码比新增的多。被整个删掉的文件有五个：

- `lib/theme.js`：深浅模式与跟随系统；
- `lib/accent.js`、`lib/accent-roles.js`：自定义主题色的运行时引擎和角色缓存；
- 奇趣、日刻各一份 `shell-accent.js`：子站接自定义色的胶水；
- 博客的 `entries/inherit.ts`：博客继承主站模式和自定义色的入口。

同步删掉的还有快捷面板的 MODE 段、相关 i18n 文案、云同步里的 mode / accent 两项，以及一批只为它们存在的 CSS。

## 测试

几层测试一起守住这次改动：

- **单测**：引擎的审计规则、22 套逐项核对、快捷面板色块、终端 `theme` 命令、云同步条目；
- **契约夹具**：`ui-cookie-contract.json` 里 36 个用例，覆盖新 cookie、旧 cookie（带 mode / accent）、坏 cookie，主站和三个子站的读端必须给出同样的结果；
- **e2e**：快捷面板没有模式段、切换浅套 / 深套整页随之变化、子站跟主站一致、系统深浅不影响页面；
- **视觉回归**：浅、深各取一套（雾霾蓝、陶土）做截图基线。因为整体配色变了，基线需要重拍一次。

## 小结

这次改动的核心是减法：把一个「可以组合出无数种样子」的系统，收成 22 个设计好、审计过的样子。灵活性少了，但每一套都是确定的——确定的颜色、确定的对比度、确定的首帧。对一个个人网站来说，我更想要后者。
