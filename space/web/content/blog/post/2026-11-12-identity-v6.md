> Part of the "Styrigx Auth Spec: How It Evolved" series, following [Account & Site Entry V3](/blog/post/2026-11-09-account-v3-site-entry/). The "two tickets" of V3 become one in this version.

V3 split "can you come in" and "can you write" into two tickets, and that kept things tidy for a while. But each ticket brought its own session, recovery key and re-verification, and stacked together they overlapped again: entry had a recovery key, the account had another; `sudo root` needed a reauth, and `sudo -v` was yet another kind of re-verification. v6 fixes exactly that: **one issuer on the site, one set of identities.**

## 1. The gateway's job changed

In V3 the gateway both issued entry sessions and decided whether a request could pass. Since v6 it only does the second:

- **Issuing**: every identity before the `@` is issued and managed by the account service. Think PAM plus `/etc/passwd`: who is who, whether a credential is right and which groups someone is in are decided in one place only.
- **Checking**: when a request arrives, the gateway asks the account service "who is this, in which groups" and decides against the route table. It signs nothing.

Sessions got simpler too. The client holds only an opaque random id in an HttpOnly, Secure, SameSite cookie; uid, groups and the identity stack live on the server, and the client token carries none of them. Since sessions are no longer signed tokens, the two signing key pairs the site used to keep had no reason to exist and were deleted.

## 2. Principle: a pyramid, not peers

The easiest mistake in design is copying. Linux is a multi-user system of peers: many people share one machine, each with a home directory, and `owner / group / other` exists to mediate between those peers.

This site is not like that. It is one person's space, **top-down and integrated in depth, a pyramid**, where permissions only flow from higher to lower. So v6 borrows Linux's vocabulary (root, su, sudo, groups, an identity stack) but not its peer model: there are no peers here, so there is no need for "other".

The host is always `space`, and the prompt is `<user>@space:<path>`. From top to bottom:

| Level | Who | What they can do |
|---|---|---|
| root | The only superuser, uid 0 | Everything; day to day only users, credentials, grants, and bulk or structural deletes |
| Owner | styrigx, uid 1000, the first regular user | Owns the site's content; profile card, avatar and preferences are his; uses sudo for admin work |
| Regular users | uid 1001 and up, created by root | Read-only: music, AI, the status card, and public content |
| Guests | Not signed in, `nobody@space` | Public content |

The everyday state is `styrigx@space`. Only real admin work calls for a single `sudo` or `su root`.

root and the owner have fully separate credentials: passwords and passkeys are registered separately, and the passkeys are named styrigx and root, so they are easy to tell apart in the phone's key manager.

## 3. Permissions are groups

The permission model is supplementary groups, with no rwx.

**The route table is the only source of permissions.** Every endpoint names one level: `public`, `user`, a group name, owner, or root. Anything not in the table is denied. The HTTP method has nothing to do with it: export is a GET but belongs to root; asking the AI is a POST but that is "use", not "write".

**The decision lives in one place**, in a fixed order of three steps:

1. A rescue session only reaches the endpoints its whitelisted commands need; everything else is denied right there.
2. root always passes, with no exceptions.
3. Everyone else is checked by route level: public is anyone, user is any signed-in identity, a group name means membership, and owner means styrigx himself.

"Rescue before root" is implemented once and shared by every entry point. Otherwise, sooner or later, some path forgets to stop rescue first.

The groups:

- `wheel`: may `su root`; `sudoers`: may `sudo`.
- `listen`, `ai`, `status`: music, the AI window, the status card.
- `curio-write`, `daymark-write`: upload, edit and single-item delete in Curio and Daymark.

The owner is in all of them by default. Regular users only get the read-only `listen`, `ai` and `status`, and the code refuses to add them to `wheel`, `sudoers` or a write group. New users start with no groups: fail-closed. Bulk and structural deletes (a whole collection, a whole app, a user, wiping data) belong to no group, only to root.

**The permission levels are the order of `man`.** The `man` index is split into root → owner → regular users → guests, and everyone sees only their own level and below. If a command is not in your `man`, it does not exist for you: typing it gives "command not found", not "permission denied". The permission boundary matches exactly what you can see.

## 4. su pushes, sudo borrows one command

There are only two ways to switch identity, with a clear split:

- **`su <user>`**: enter the target user's credentials and switch, **pushing the stack**. A guest can `su` to the owner or a regular user; `su root` is only for `wheel` members and takes root's credentials. Regular users cannot `su` to each other; to switch, `exit` back to guest first.
- **`sudo <command>`**: someone in `sudoers` enters **their own** credentials each time and borrows root for that one command. No ticket is issued and nothing is pushed.

`exit` pops one level (root → owner → guest), and `lock` clears the whole stack and deletes the server-side session. `who` shows the full stack path, such as `root via styrigx`. The stack holds at most three levels and lives on the server.

Public sign-in as root is forbidden in code: a sign-in started by a guest never issues uid 0, and the public sign-in endpoint rejects root's credentials outright. The only way to root is to become the owner first, then `su root`.

Entry no longer redirects either. Before, an unauthenticated visit sent you to the lock screen and back to the original page afterwards; now you `su` right where you are, and the page stays put.

### Session lifetimes

| Level | Lifetime |
|---|---|
| Owner | 30 days, sliding; renewed only when less than half is left, at most one write per session per day |
| root | At most 1 hour; 15 minutes of foreground idle drops back to the owner, and the timer pauses while the page is hidden or the screen is locked |
| Rescue | 15 minutes, never renewed |

Renewal for the owner level is throttled: checking a request only reads, so not every request writes to the database.

## 5. sudo cannot take root

The owner is in `sudoers`, so whoever gets the owner's credentials can do nearly any damage root can, through `sudo`. The pyramid model has to face this squarely: **the real boundary is the owner's credentials, and they must be guarded as closely as root's.**

But there is one thing `sudo` cannot do: touch root's own credentials. `sudo passwd root` and adding or removing root's passkeys through sudo are always refused; changing root's credentials requires root to be the top of the current stack (`su root` or a rescue session).

So even if the owner's credentials are stolen, the attacker can do damage through sudo but cannot take root. I reset the owner's credentials as root and I'm back, without touching the recovery key. The cost is one check and one test.

A few related guardrails:

- root cannot be deleted, and neither can the owner (the profile card would have no owner);
- removing the last member of `wheel` or `sudoers` warns you: after that, the recovery key is the only way to root.

## 6. User management

root manages regular users with Linux-style commands:

- `useradd <name> [-e date] [-G groups]`: generates a random one-time password of 16+ characters, shown once, with only its hash stored; the first sign-in forces a change, and the one-time password expires after 24 hours. `-e` follows Linux semantics: the account stops working at 00:00 (Shanghai time) on that day.
- `userdel <name>`: clears sessions, credentials and groups; the user row is not deleted but renamed to a tombstone and disabled. uids are never reused, so a new user never inherits data under an old uid. The name can be used again.
- `usermod -aG / -rG`: add or remove groups.
- `passwd <name>`: issues a new one-time password and ends all of that user's sessions.
- Expiry: the account is disabled and its sessions ended; after a 30-day grace period it is deleted the same way as `userdel`.

The owner manages his own credentials with `passwd` and `passkey`; regular users can only change their own password with `passwd` and cannot manage passkeys. Changing your own password asks for the current one first; passkeys carry their own WebAuthn check.

This also replaces V3's share links. To show someone something, I used to send a time-limited short link; now root creates a time-limited regular user. Share links are gone entirely; proxy subscriptions at `/s/<token>/<source>` stay.

## 7. One recovery key

V3 had two recovery keys; v6 has one, and it only covers root. A regular user who forgets a password gets reset by root.

The key lives in Cloudflare Secrets Store. At runtime the Worker can only read it; the code contains no write or delete call, and a static check runs before merging. I set and change the value in the dashboard, and it takes effect immediately, without a redeploy.

Rescue works like single-user mode:

1. A guest types `rescue`, then the recovery key;
2. The Worker does a constant-time comparison and, if it matches, issues a one-time root session for 15 minutes, never renewed;
3. The rescue session accepts only a whitelist: `passwd`, `passkey`, `whoami`, `groups`, `exit`, `lock`. Changing the key is not on it;
4. Afterwards it reminds me to set a new value in the dashboard.

Each successful rescue records a hash fingerprint of the key (never the key itself), kept forever; the same value is refused if used again. If the fingerprint cannot be written, rescue is refused: fail-closed. Lost everything? If I can sign in to Cloudflare, I set a new value. There is no break-glass.

## 8. The visible part

Unifying identity isn't only a back-end matter. The interface has to show "who am I right now" at a glance.

**The avatar is whoami.** The site has one configuration (avatar, preferences, profile card), owned by the owner and held jointly by root as superuser. Everyone sees the avatar the owner set, but the corner mark differs: root gets a `#` at the bottom right and the owner a `$`, matching the end of the terminal prompt; regular users and guests get none. The owner and root open the account page by tapping the avatar; for regular users it is decoration and does nothing.

**The shield is an identity badge.** The shield in the top bar has four levels, filled more as identity rises: an empty shield for guests, a small figure inside for regular users, a check for the owner, and a solid shield that keeps the check for root. The owner and root use the theme color; guests and regular users use grey. Tapping the shield never switches identity directly; it only prefills the next command in the terminal, which runs on Enter: if you can go up it prefills the promotion (guest `su `, owner `su root`), and at the top it prefills `exit`.

**The prompt follows identity.** The terminal, the question line in the AI window and the decorative prompts across the site all show the current identity: guests `nobody@space:~$`, the owner `styrigx@space:~$`, regular users `<name>@space:~$`, and root with `#`.

**The account page has three things left**: the profile card, the devices card and a `lock` button. There is no account security card: passwords and passkeys are managed only in the terminal with `passwd` and `passkey`. Admin changes on the account page (such as signing out a device) only prefill the command in the terminal: `sudo …` for the owner, no sudo for root, and input and verification both happen in the terminal.

Curio's and Daymark's import pages got simpler too: the old "verify" button is gone, the import button itself is the trigger and the server checks the session; if you aren't signed in, the top-bar terminal opens with `su ` prefilled.

## 9. Security details

- **No enumeration**: a missing user and a wrong credential return the same error along the same timing path; nothing reveals which verification methods a user has.
- **Two-dimensional rate limits**: a hard cap of 6 per minute per IP; progressive backoff per account, one bucket each, waiting 1 second after the first failure, then 5 seconds, 30 seconds and 5 minutes, with no hard lockout. All rescue attempts share root's bucket. Passkeys don't count toward cooldowns. Checking a request only reads; counts are written only on failed authentication.
- **Hashing**: a fast salted and peppered hash, not bcrypt or argon2. A Cloudflare Worker gets 10 ms of CPU per request, which slow hashes can't fit in; online guessing is stopped by rate limits. The site keeps a single pepper.
- **epoch**: any change to credentials, groups or expiry increments it, compared strictly. Changing your own password keeps the current session alive; when root resets someone else, all of that user's sessions end.
- **fail-closed**: an unauthenticated request to any endpoint not in the route table gets 401; the gateway no longer writes identity headers downstream, and sub-apps decide from the session themselves.
- **Audit**: useradd / userdel / usermod / passwd, su, sudo, rescue and failed sign-ins record uid, command, time and IP prefix, kept for 90 days; root's privileged content operations are recorded too.
- **One query**: checking a request reads the database once, getting session, user, groups and epoch in a single JOIN.

## 10. How the cutover went

There was no conversion between old and new formats. The cutover went in stages, old and new running side by side, and the old was deleted only after rescue worked:

1. **P1**: tables, the group model and the single decision function, and an inventory of every route (77, plus 11 reachable only through service bindings).
2. **P2**: su, sudo, exit, lock, the user management commands, the identity stack, the foreground idle timer, and an avatar that follows identity.
3. **P3**: the `rescue` entry went live and was tested end to end.
4. **P4**: delete the old. Share links, the old entry issuer, the old re-verification, two old recovery keys, two signing key pairs, app grants and the whole screen-time feature went, along with their old tables and data, with no compatibility layer left behind.

Each stage was its own PR, merged only with CI fully green; before deleting a secret the deploy had to be green first, and after deleting it, that deploy became the rollback floor.

## Closing

V3 fixed "one ticket doing two jobs". v6 fixes "two sets of tickets stacked on each other". The site now has one issuer, one set of identities and one recovery key; permissions flow from the top down, and what you see in `man` is what you can do.

The gateway is still here; it has gone from issuing tickets to checking them. And this series doesn't stop here.
