The previous post was about the redesign you can see. This one is about the half you can't: the repo, deployment and data. No screenshots here, but this part decides how much effort every future change will cost.

## Before: one repo per site

At first every site had its own repo and subdomain: the main site, `blog.styrigx.com`, `book.styrigx.com`, and later a separate repo hosting Curio and Daymark. Each site had its own Pages project and synced its own copy of the shared shell (the top bar, panels and palettes).

The problems showed up quickly:

- The shell copies drifted apart all the time; changing one button meant four PRs.
- The lock screen had to share a session across subdomains: cookies, public-key distribution, cross-site redirects. Lots of ways to fail.
- Four builds, four CI setups, four sets of dependency upgrades.

## Now: one repo, one domain, one Hugo site

From late October to November 8 the merge went in several steps:

1. All sub-site code moved into the main repo, and the old repos were archived.
2. Sub-sites moved under one domain, split by path: `/blog/`, `/curio/`, `/daymark/`. The old subdomains went offline.
3. The last step merged all four into **one Hugo site**: one config, one build, one Pages project.

The shared shell is no longer copied. Sub-sites use the main site's templates and scripts directly; a handful of derived files are generated by a script, and CI checks they match their source.

The cost, stated plainly: if any one site fails to build, none of the four ships. And the Chinese URLs of sub-site pages have to be set explicitly in front matter, and getting one wrong fails the build. I can live with that. I'd rather fail early and loudly.

## The L series: renaming and moving the entry backend

Once the entry V3 design was settled (see the other post), the backend needed the same treatment. I split it into five PRs, shipped in order:

- **L0**: Daymark data had a marker value called `admin` that really meant "written under an account grant". It became `grant`, freeing the word `admin` (the entry side's identity uses it in code).
- **L1**: the new entry UI: `sudo styrigx`, the shield menu, environment prompts.
- **L2**: the entry backend was renamed space-core, matching the `<site>-core` naming of Curio and Daymark. The share-link service, which had been its own Worker, was folded into core.
- **L2b**: data moved to the new core database and KV; service monitoring got a database of its own.
- **L3**: the one-off migration code that only existed for the cutover was deleted, and automatic rollback got a floor so it can never roll back to a version from before the database switch.

Why split monitoring out? Two days earlier I had merged the gateway, share-link and monitoring databases into one, and now I separated them again. The rule I eventually landed on: **anything about entering the site goes into core; anything functionally independent of the site (account, AI, monitoring, proxy rules) stands on its own.** When I merged the databases I was only thinking "one fewer resource" and hadn't thought the boundary through.

There are now seven Workers: site core, account, AI, monitoring, Curio, Daymark and proxy rules. Only site core sits on the site-wide route. The others either handle their own API paths or have no public route at all and are reached only through service bindings.

The cutover had a price: rotating the signing keys and password peppers sent every device back to the lock screen once and invalidated old temporary keys. That was a one-time cost accepted at design time.

## The big cleanup

After the L series shipped and checked out, it was time to delete things. One rule: **first confirm nothing in main's code or config reads it, then delete it.**

On the platforms:

- Cloudflare: two old Workers, the old database, the old KV, an old deploy token, a batch of old secrets nothing read any more, and 8 long-empty legacy tables in the account database.
- GitHub: two old deployment environments, twenty-odd merged or closed branches, and a pile of stale Actions caches and build artifacts.

In the repo:

- Unreferenced one-off scripts, old test fixtures, and JS and template fragments that never made it into a build were removed. Before deleting, I built both the branch and main and compared the output file by file. The only difference was a build timestamp, so the pages didn't change at all.

## The docs, rewritten as a spec book

`docs/` used to be a pile of task briefs, design drafts and superseded plans, old and new mixed together. Readers, AI agents included, couldn't tell which was current. This time I reorganised the whole thing:

- Folders by purpose: architecture, specs, security, design, operations, contributing, plus decision records (ADRs).
- Every document opens with a number, version, date and status; normative words follow RFC 2119.
- **Code wins.** The docs describe what the code on main does. When they disagree, the code is right, and the doc gets fixed in the same PR or the one right after.
- **Outdated means rewrite.** Stale documents are rewritten or deleted, with no "historical" copies kept around; the backstory goes into an ADR or stays in git history.
- Only names of resources and secrets are written down, never values or internal ids.

While reorganising I checked the docs against the code and found about ten mismatches, all fixed to match the code. Four ADRs record the biggest decisions of this period: one repo and one site, how the lock screen evolved, account and entry V3, and the choice of AI models.

Finally I rewrote the root README (Chinese and English) and re-shot 16 screenshots (home, lock screen, AI and blog, on phone and DeX, in both languages).

## A closing thought

Most of the platform work and code over these few days was done by an AI agent within the scope I approved: moving databases, renaming, deleting resources, opening PRs, watching CI. My part was settling the design, creating the secrets and approving merges. I could let go that much because of the rules set up earlier: everything goes through PRs, nothing is pushed straight to main, merges only on green CI, secret values only ever pass through my hands, and nothing gets deleted until it's proven unused.
