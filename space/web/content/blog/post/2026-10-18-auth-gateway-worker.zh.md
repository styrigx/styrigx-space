> 本文是「styrigx 鉴权体系规范的变迁」系列的一篇，接在《鉴权规范 2.0》之后。这一版没有成文的定稿，按当时的 PR 记录整理。

前两篇讲的都是「票长什么样」：几对钥匙、几种会话、谁签谁验。到 10 月中旬，票的设计基本稳住了，问题换成了另一个：**鉴权代码住在哪里**。

## 一、当时的问题

那时鉴权写在主站 Pages Functions 的中间件里。博客、书架这些子站也要验票，于是各自也带一份中间件、一份公钥，部署时各配各的变量。几个后果：

- 同一套逻辑散在好几个仓库，改一处要同步几处，漏一处就是一个洞；
- 私密值和静态页面放在同一个 Pages 项目里，边界不清楚；
- 子站要不要验票、怎么验，靠各自记得，没有一处能说清「这个站整体是怎么拦的」。

我当时的原话是：一开始的任务就是把鉴权完全独立出去。只把 `/api/*` 迁过去、页面还留在 Pages 里验的做法，被我否掉了。

## 二、做了什么

### 鉴权变成一个独立 Worker

新建 Worker `styrigx-auth-gateway`，挂在整站通配路由上，所有请求先过它，再决定放不放。Pages 退回成只放静态文件的地方。

### 私密值只进 Secrets Store

签名私钥这类私密值迁进 Cloudflare Secrets Store，只有网关在运行时读取。Pages 只留公开变量；CI 加了检查，私密值一旦又出现在 Pages 配置里就失败。

部署网关用的 GitHub 环境和部署凭据由我亲手建，只允许从 main 部署。

### 子站「零钥匙」

子站 Pages 删掉自己的中间件，手里不再有任何钥匙。页面的会话检查、验票，统统由网关回答；子站自己的 API 拆成独立 Worker 的，也通过服务绑定去问网关。

子站的 CI 加了一道门：部署前先确认网关已经挂在这个站上，没挂就不部署。宁可不上线，也不让一个没人守的站上线。

### 分步上线

没有一次切过去。顺序是：

1. 网关先部署，但不接线上流量，只接一个无关紧要的接口试水；
2. 接管主站的 `/api/*`；
3. 接管主站全部页面，Pages 只放静态文件；
4. 子站一个一个接进来：先博客和书架，几天后是奇趣和日刻。

每一步都等上一步的部署全绿、冒烟通过再走。CI 还会核对每个页面都有路由，静态资源则不过网关，省一次 Worker 调用。

## 三、为什么这么做

- **一处判定。** 整站怎么拦，只看网关一处。以后改规则，不再是「改主站、再改三个子站」。
- **钥匙离页面远一点。** 静态页面的部署和私密值彻底分开，Pages 出问题也拿不到钥匙。
- **fail-closed 有了落脚点。** 网关对没认证的 `/api/*` 一律先回 401，连接口存不存在都不透露。后来删掉的接口在外面看也是 401 而不是 404，这是有意的。

## 四、没改的东西

这一版只是搬家。上一篇的根凭证、站长凭证、锁屏凭证，门和票，原样搬进了网关。概念上的问题（站长凭证到底是什么，stepup 和应用凭证要不要）一个都没碰，留到了下一版。

## 后来

网关后来改过名，也吞并过分享服务，再后来在 v6 里从「签发加判定」变成「只判定不签发」。但「整站一个入口、子站零钥匙」这条，从这一天起就没变过。
