## 0. 摘要

Styrigx 由一个主站（styrigx.com）和若干子站（blog、book，以及以后的应用）组成，共用 `.styrigx.com` 下的登录状态。本规范定义这套站点群里**所有签名密钥**的命名、用途、存放位置、签发与验证方，以及轮换和事故响应流程。

核心原则只有四条：

1. **一种用途一对密钥**，绝不跨用途复用。
2. **只有主站签发**，子站永远只持公钥。
3. **缺配置即拒绝**（fail closed），任何密钥缺失都不会变成放行。
4. **所有凭证可过期、可撤销**：每张凭证带有效期和会话纪元（epoch），一键「锁定所有设备」即可全部作废。

## 1. 适用范围与角色

| 角色 | 说明 |
|---|---|
| 主站（space） | 唯一的签发方，持有全部私钥，负责解锁、二次验证和发放子站通行证 |
| 子站（blog、book 等） | 只验证，不签发；只持自己需要的公钥 |
| 所有者（owner） | 唯一能解锁和执行敏感操作的人 |
| 访客（visitor） | 可浏览公开内容，任何敏感操作一律拒绝 |
| CI | 每次运行临时生成测试密钥，只写入预览环境 |

## 2. 威胁模型

本规范要防的是：

- **凭证伪造**：没有私钥的人构造出能通过验证的 cookie。
- **凭证越权**：一张低权限凭证被拿去做高权限的事，例如用登录 cookie 改密码，或用主站的二次验证凭证去子站上传。
- **凭证长期有效**：设备丢失或 cookie 泄露后，旧凭证仍能使用。
- **子站失守连带主站**：某个子站的配置或代码泄露，导致攻击者能签发凭证。
- **配置缺失导致放行**：部署时漏配变量，系统默认放行。

不在本规范范围内：Cloudflare 账号本身被接管、所有者设备被完全控制、浏览器零日漏洞。

## 3. 命名规则

```
SGX_<用途>_PRIVATE   私钥（PKCS8 PEM）
SGX_<用途>_PUBLIC    公钥（SPKI PEM）
```

本地文件名对应为 `<用途>.key` 和 `<用途>.pub`。变量名只表达用途，不表达算法——算法统一为 Ed25519，写进名字反而让人看不出这把钥匙管什么。

## 4. 三对密钥

| 中文名 | 变量 | 签发的凭证 | 有效期 | 私钥在 | 公钥在 | 管什么 |
|---|---|---|---|---|---|---|
| 锁屏密钥 | `SGX_LOCK_PRIVATE` / `SGX_LOCK_PUBLIC` | `sgx-verified` | owner 12 小时，visitor 1 小时 | 主站 | 主站、全部子站 | 三站解锁状态 |
| 主站密钥 | `SGX_STEPUP_PRIVATE` / `SGX_STEPUP_PUBLIC` | `sgx-stepup` | 10 分钟 | 主站 | 主站 | 主站敏感操作：改密码、增删通行密钥 |
| APP 密钥 | `SGX_APP_PRIVATE` / `SGX_APP_PUBLIC` | `sgx-app` | 10 分钟 | 主站 | 需要的子站（目前只有 book） | 子站敏感操作：book 上传书 |

### 4.1 为什么是三对，而不是一对

- **泄露隔离**：任何一对出问题，只影响它自己的用途，轮换也只动它自己。
- **天然防越权**：三种凭证用不同私钥签名，一张 `sgx-verified` 在密码学上就不可能通过 `sgx-stepup` 或 `sgx-app` 的验证，不依赖代码里有没有写对类型判断。
- **最小暴露**：主站公钥只在主站，子站根本不知道它；APP 公钥只发给真正需要的子站。

### 4.2 凭证格式

所有凭证都是点分字符串，最后一段是对前面全部内容的 Ed25519 签名（base64url）：

```
sgx-verified = role.epoch.exp.sig
sgx-stepup   = owner.epoch.iat.exp.sig
sgx-app      = owner.aud.scope.epoch.iat.exp.sig
```

- `role`：`owner` 或 `visitor`；`sgx-stepup` 和 `sgx-app` 只签给 owner。
- `epoch`：会话纪元，见第 6 节。
- `iat` / `exp`：签发时间和到期时间（毫秒）。
- `aud` / `scope`：通行证给哪个子站、做哪件事，例如 `book` / `upload`，由主站白名单限定。

cookie 属性统一为 `Domain=.styrigx.com; Path=/; HttpOnly; Secure`；`sgx-verified` 用 `SameSite=Lax`，`sgx-stepup` 和 `sgx-app` 用 `SameSite=Strict`。

## 5. 签发与验证流程

### 5.1 解锁

1. 访问任一站点，未持有效 `sgx-verified` → 跳回主站锁屏。
2. 所有者用密码或通行密钥解锁 → 主站用锁屏私钥签发 `sgx-verified`。
3. 各站用锁屏公钥验签，并检查未过期、epoch 不低于主站当前值。

### 5.2 主站敏感操作

1. 已解锁的所有者发起敏感操作，没有有效 `sgx-stepup` → 返回 `stepup-required`。
2. 前端弹出通行密钥验证，强制用户验证（UV），challenge 按用途隔离、单次使用。
3. 通过后主站用主站私钥签发 `sgx-stepup`，前端自动重试原操作。
4. 改密码、删除密码或删除通行密钥成功后立即清除 `sgx-stepup`。

例外：还没有任何通行密钥时注册第一把不要求二次验证，否则永远加不上；「锁定所有设备」是紧急按钮，只会减少权限，不设门槛。

### 5.3 子站敏感操作（以 book 上传为例）

1. book 发现没有有效 `sgx-app` → 跳到主站 `/stepup?aud=book&scope=upload&return=…`。
2. 主站要求 owner 会话 + 有效 `sgx-stepup`（没有就先做 5.2），再用 APP 私钥签发 `aud=book, scope=upload` 的 `sgx-app`，跳回 book。
3. book 用 APP 公钥验签，检查 owner、aud、scope、有效期和 epoch，通过后创建上传任务。
4. 上传任务在服务端登记 2 小时，后续分片只需会话 + 有效任务号，大文件不会因通行证过期中断。

## 6. 撤销：会话纪元（epoch）

主站在 KV 里保存一个单调递增的整数 `session-epoch`，每张凭证都带签发时的值。

- 「锁定所有设备」把 epoch 加一，**三种凭证同时失效**。
- 子站通过主站 `/api/session-epoch` 获取最新值，内存缓存 60 秒。
- 读取失败且无缓存时拒绝；KV 读取出错时接口返回 503，绝不当作 0，也绝不写入更小的值。

## 7. 存放与配置

| 项目 | 变量 | 类型 |
|---|---|---|
| 主站 | `SGX_LOCK_PRIVATE`、`SGX_STEPUP_PRIVATE`、`SGX_APP_PRIVATE` | Secret |
| 主站 | `SGX_LOCK_PUBLIC`、`SGX_STEPUP_PUBLIC`、`SGX_APP_PUBLIC` | Text |
| blog | `SGX_LOCK_PUBLIC` | Text |
| book | `SGX_LOCK_PUBLIC`、`SGX_APP_PUBLIC` | Text |

规则：

- 私钥用 Secret 配置；公钥用 Text 配置（公钥不是秘密，控制台可见便于核对三站一致），但同样不写进仓库或 `wrangler.toml`。
- 私钥另存一份在密码管理器，按「锁屏密钥 / 主站密钥 / APP 密钥」分条保存。
- 生产与预览环境的密钥完全分开；CI 每次临时生成，用完即弃。
- 以后新增子站：只配 `SGX_LOCK_PUBLIC` 和 `SGX_SITE`；需要敏感操作时再加入应用密钥的 aud 白名单并配 `SGX_APP_PUBLIC`。

生成方式：

```
openssl genpkey -algorithm ed25519 -out <用途>.key
openssl pkey -in <用途>.key -pubout -out <用途>.pub
```

## 8. 失败行为（fail closed）

| 情况 | 行为 |
|---|---|
| 缺锁屏公钥 | 页面跳锁屏，API 401，只放白名单路径 |
| 缺任一私钥 | 拒绝签发对应凭证，返回 500，不降级 |
| 缺主站或 APP 公钥 | 对应敏感操作一律 403 |
| epoch 拿不到且无缓存 | 拒绝 |
| KV 读取出错 | 503，不写入 |
| 签名不符、过期、epoch 过旧、aud 或 scope 不符、role 不是 owner | 拒绝 |

没有任何「未配置就放行」的开关，测试也不靠放行通过。

## 9. 轮换

**计划轮换**（建议每年一次，或更换设备、协作方式时）：

1. 生成新密钥对。
2. 在对应项目同时配上新私钥和新公钥。
3. 部署主站，再部署子站。
4. epoch 加一，让旧凭证全部失效。
5. 所有设备重新解锁，确认正常后从密码管理器删除旧密钥。

**紧急轮换**（怀疑私钥泄露）：立即执行上面 1 至 4 步，先换密钥再排查原因；只换出问题的那一对，其余两对不动。

## 10. 验收要求

每个涉及密钥的改动都必须有功能测试覆盖：

- 缺变量 fail closed。
- 过期、epoch 变更、篡改、伪造签名、visitor 全部被拒。
- 跨用途被拒：`sgx-verified` 不能当 `sgx-stepup` 或 `sgx-app`；`sgx-stepup` 不能当 `sgx-app`；aud 或 scope 不符被拒。
- 有效凭证通过；上传任务在通行证过期后仍能完成。

合并标准为正式 CI 全绿，视觉基线的变化不能替代功能断言。

## 附录：术语

- **Ed25519**：一种椭圆曲线签名算法，密钥短、验证快、不需要额外参数。
- **fail closed**：出错或缺配置时拒绝，而不是放行。
- **epoch**：会话纪元，用来一次性作废所有已签发的凭证。
- **UV（User Verification）**：通行密钥验证时要求本人生物识别或 PIN，而不仅仅是「设备在场」。
- **aud / scope**：通行证的使用对象和用途，限定一张凭证只能在哪个站点做哪件事。
